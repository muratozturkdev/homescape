# Homescape: CLAUDE.md

The single context source for this project: architecture, rules and pitfalls for contributors and AI coding agents. Read it at the start of every session. Visual details live in `DESIGN.md`. An explicit instruction from the person you are working with takes precedence over both.

Writing rule (everywhere: code, UI text, docs, commits): no em dash or en dash characters. Use a colon, comma, semicolon or a new sentence; use a plain hyphen for ranges.

---

## 1. Product

**Homescape** is a web app that shows a Home Assistant (HA) home in the browser as a 3D dollhouse and lets you control it.

- **View mode:** rooms and items follow HA states: lights glow (at night they cast real light), the TV screen turns on, the AC blows air, the diffuser emits mist, a door opens when its sensor opens, a motion sensor sends ripples across the floor, the robot vacuum roams. Hovering a bound item shows a quick on/off pill (on touch, a tap toggles); clicking opens that device's controls in the right card (on/off, brightness, color, target temperature, cover position, alarm mode...). Unbound items are not clickable. Top bar: home and floor switchers, Dashboard (every control, room by room), search (⌘K), first-person walk (Walk).
- **Edit mode (directly in 3D, like a game):** drag a card from the build bar at the bottom into the scene (tabs: Rooms, then the item groups: Lights, Climate, Media, Security, Sensors, Smart devices, Kitchen and appliances, Bathroom, Furniture, Desk and decor, Pets, Garden and balcony, Garage and vehicles, Doors and windows; a search box; every card shows a real 3D thumbnail). A green ghost can be dropped, a red one says why not. Select a room and drag to move it (its items come along), resize it with edge handles, rotate it 90° with all its parts and items with R (⇧R reverse) or "Rotate" in its card (`ui/rotateRoom.ts`; it does not rotate if it would overlap another room). Rooms **never overlap**. Drag items to move them (wall items snap to the nearest wall), rotate, delete, duplicate; bind any number of HA entities to an item; bind a room to an HA area. Undo / redo.
- **Item ↔ HA binding:** items are added **independently** of HA; HA features are attached afterwards. Any entity can be bound to any item (furniture too: an occupancy sensor on a bed, a plug on the fridge). The first bound entity is the **main** one: it drives the 3D look (on/off, light, door open) and the main control; the others are **extras** (temperature + humidity sensors on an AC, lock + door sensor on a door) that the card reads or controls. An entity's kind (Temperature, Humidity, Power, Battery...) comes from HA's `device_class`; users never classify. The picker shows suggestions first (fitting domain, companion device classes, same HA area as the room); "All entities" shows everything.
- **Doors:** rooms have real doors; walls open for doors and windows. The auto plan adds interior doors so every room is reachable; in Edit, "Complete interior doors" in the toolbar adds missing ones. A door's swing area must stay free (placement rule).
- **Build from Home Assistant:** once connected, rooms are created from HA areas and items from entities; the user edits afterwards. This is what makes Homescape work with anyone's HA.
- **Start from scratch:** the eraser button in the Edit toolbar opens a confirmation; the plan (rooms, items, doors, bindings) is cleared and the house is drawn again on empty ground. The cleared plan is backed up automatically (`backup`, persistent) and comes back with "Restore previous plan"; it can also be downloaded as JSON. HA connection and theme are untouched. On an empty plan: a hint in the middle of the scene, the build bar opens on Rooms, the right card shows a step-by-step guide, "Set up automatically from Home Assistant areas" and the list of unbound HA devices (each placed with one click).
- **Saving:** every change is written immediately to the browser's localStorage (`homescape-layout-v1`); reloading and closing the browser are safe. Limits: only that browser and that origin (`localhost:5190` and `<LAN IP>:5190` are separate stores); lost when site data is cleared or in a private window. Backup: "Export plan" (JSON) or Plan history > Download all homes. While connected to a live HA, the plan is also stored under the HA user (see "Plan sync across devices"). If `localStorage.setItem` fails, editing goes on and a notice appears (event `homescape:storage-failed`).
- **Day / night:** automatic (night when HA's `sun.sun` is below the horizon), or forced day or night.
- **Plan view:** a top-down floor plan.

### Key decisions

| Topic | Decision |
| --- | --- |
| Distribution | A plain web app that also runs inside Home Assistant: as an app (add-ons were renamed Apps in Home Assistant 2026.2) with an ingress panel, or as built files in `/config/www` behind a Webpage dashboard (section 4). |
| Editing | Directly in 3D (no 2D plan editor). Precision comes from the top-down plan view and 0.25 m / 0.05 m snapping. |
| Test data | A real HA may be read read-only (for example through an MCP server). Never call services, never change settings. |
| Name | Homescape (package `homescape`). |
| Visual language | A pastel isometric dollhouse plus its night version. |
| Icons | Lucide (`lucide-react`) for every UI icon. |
| Technology | Vite + React, not Next.js: the app serves static files under an ingress subpath, where a server-side framework is in the way. React keeps the code modular anyway. |
| Language | Code and source UI text in English; translations through `src/i18n` (section 8). |

## 3. Working method: the see-and-fix loop (mandatory)

1. Clarify the target (`DESIGN.md` art direction; `reference/target.png` if present).
2. Write the code; every object from basic geometry, no external models or textures.
3. With the dev server running, take a screenshot with `npm run shot` and open the PNG.
4. Compare it with the target, list the differences, fix them, shoot again.

Rules:

- A visual change is not done until a screenshot confirms it. At least: day overview, night overview, a room in Edit mode, phone (390x844).
- For state visuals, select the device (`SHOT_ITEM=switch.xxx`). The demo source imitates service calls; sensors trigger by themselves now and then.
- Clear every console error in the `shot` output. Known harmless warning: `THREE.Clock ... deprecated` (from inside React Three Fiber).
- Test hook: `window.__homescape` (`src/App.tsx`, see "Test hook" in section 5). Ready marker: `body[data-ready="1"]`. Extend the hook when you add an interaction.

### Connection (the most important part)

All HA access goes through the `HaSource` interface: `subscribe`, `callService`, `registry`, `close`, plus `userData` (live only: per-user storage for plan sync) and `inject` (demo only: test entities). The rest of the app does not know whether the source is demo or live.

- **Demo data:** `src/demo/snapshot.ts` uses `local-snapshot.json` when present (a read-only snapshot of your own HA; it contains real entity names, so it is git-ignored), otherwise the generic `sample-snapshot.json`. Demo names (the sample snapshot and `american.ts`) are English source text translated at load time with `t()` (`SAMPLE_TEXTS` in `snapshot.ts`); a personal snapshot is shown as it is.
- **Live, in development:** with `HA_URL` set, Vite proxies `/api` (WebSocket included), `/auth`, `/frontend_latest`, `/static` and similar paths to HA. The browser sees everything on `localhost:5190`, so no CORS setting is needed and HA's own login page works. Check: `curl localhost:5190/api/` gives 401, `/auth/providers` gives JSON.
- **Live, hosted elsewhere:** when the app is opened from another origin, the user adds that origin under `http: cors_allowed_origins:` in HA's `configuration.yaml`. That is the user's job; the app (and any AI agent) never changes HA settings.
- **Inside Home Assistant** (`ha/embed.ts`, `docs/home-assistant.md`): as an app panel (ingress) or a Webpage dashboard pointing at `/local/homescape/index.html`. Both load the app in a same-origin iframe of the HA frontend, so it reuses the frontend's authenticated connection (`window.parent.hassConnection`): no second login, no stored token. Opened from HA's address without the frontend around it (`/local/...`, an ingress path or `/hacsfiles/...`; `servedByHomeAssistant`), it signs in through HA's login page at that address.
- **Sign-in:** the recommended path is OAuth: `getAuth({ hassUrl })` sends the user to HA's login page; on return `?auth_callback=1` yields the token, stored in `localStorage['homescape-auth']`. Second path: a long-lived token the user created in their HA profile (optional "remember"). **An AI agent never enters a password or token on the user's behalf; the person runs live connection tests.**
- **Registry:** `config/area_registry/list`, `config/entity_registry/list`, `config/device_registry/list`. An entity's area is its own, else its device's. Hidden, disabled, config and diagnostic entities are left out of the auto plan. If a non-admin user cannot read the registry, the plan still works.

### Running inside Home Assistant

`base: './'` and the static `dist/` let the same build be served under an ingress subpath or from `/config/www/homescape`. The Home Assistant app (`homescape/`; the folder name equals the slug) is a small nginx image that serves the files on port 8099 to the ingress proxy only; with `ingress: true` it becomes a panel in the HA sidebar. It uses prebuilt files from `homescape/www/` (`npm run build:app`) when present, otherwise it builds the web app from the repository (`ARG HOMESCAPE_REPO`, `HOMESCAPE_REF` in its Dockerfile; `build.yaml` and `BUILD_FROM` are gone from current Supervisors, and only `amd64` and `aarch64` are supported). `panel_admin: false` shows the panel to every user. Same origin, so no CORS and no separate login. The plan lives in the browser and syncs through HA user data (`frontend/set_user_data`), see "Plan sync across devices".

### State and persistence

- `useLayout` (`homescape-layout-v1`): plan, active floor, theme, unplaced entities. While dragging, not every frame goes into history: `checkpoint()` at the start, then `record: false`. The persist version is `STORE_VERSION` (5). Migrations (`migrate`, helpers in `model/migrate.ts` and the files named below): version 0 plans get interior doors once via `connectRooms`; version 1 folds TV backlight strips into the TV (`foldTvBacklights`); version 3 `settleWallItems`; version 4 `splitTvUnits`; version 5 `primaryFirst`.
- **Storage protection (RULE):** a half-written migration in `layoutStore.ts` was once saved while the app was open; Vite HMR re-ran the module and re-read the stored plan, `migrate` threw, zustand did not load the plan, `useAutoLayout` built the demo home and overwrote the saved plan. Now: (1) `guardedStorage` copies the raw stored value to `homescape-layout-v1-backup-s<version>` before an old version is migrated; (2) every migration step runs inside `step()` and never throws (the plan then loads unmigrated); (3) if loading still fails (`onRehydrateStorage` error, broken JSON), the raw value is copied to `homescape-layout-v1-rescue`. Tests check all three. Older builds used other names for these keys; `renameBackupKeys` moves them over once at startup. **Always save `layoutStore.ts` (migrations above all) in one go, in a compiling state**; a multi-step edit can wipe real data in an open page. To recover, write the raw JSON from those keys back to `homescape-layout-v1`. The plan schema (`Layout.version`) is still 1; optional fields such as `Item.extras` let old plans and JSON files open as they are.
- `clearAll()` builds an empty plan (`emptyLayout()`: one floor, no rooms; the layout is NOT null, otherwise the auto plan rebuilds it), moves the previous plan into `backup` if it had content, and switches to Edit. `restoreBackup()` brings the backup back (the current plan goes into undo history) and deletes it. Undo history (`past`) is not persistent, so the persistent `backup` is the safety net for clearing.
- The "devices not bound to any item" list is recomputed on the fly (`Inspector > useUnboundDevices`): entities that `kindFor` can place, not in `registry.skip`, and not bound (main or extra) to any item. The stored `unplaced` field remains only for backward compatibility.
- Binding operations live in the store: `bind` (main if empty, else extra; removes the entity from unplaced), `unbind` (if the main entity goes, the first extra becomes main), `makeMain`. Pure helpers in `model/bindings.ts` (`bindingsOf`, `boundAnywhere`, `withBinding`...).
- An item's display name (`ui/Bindings.tsx > itemName`): the user's name; else the main entity's name if that entity is the item itself (its domain is in `CATALOG[kind].domains`); else the kind label. A sensor bound to a sofa does not rename the sofa. Binding never changes the item's name.
- `useHa`: connection, entities, registry; settings in `homescape-connection`.
- `useView`: plan view and framing requests (`request({ kind: 'room', id })`).
- `usePlacement`: the build bar card in use (`target`), `via` ('drag' | 'click'), rotation with R, pointer, ghost result (`result`), validity of the item being moved (`moving`). Not persistent.
- `useThumbs`: thumbnail data URLs (generated once per session; holds no three code, stays in the main bundle).
- On first open without a plan, `useAutoLayout` builds one from the connected source's areas.

## 5. 3D rules

### Basics

- **No assets, everything is code.** No external models, textures or HDRs are loaded. Textures are drawn on canvases in `kit/textures.ts`. Randomness through `rng(seed)`.
- **Coordinates:** meters; x to the right, z forward (toward the camera), y up. A room is its back-left corner `(x, z)` + `w`, `d`. In item space the origin is the center of the footprint on the floor and the front faces +z; wall items have their back at -z. Exception `ledStrip`: its origin is the strip itself, its height `item.y` or `DEFAULT_Y`.
- **Visual state:** `ItemNode` derives a `Visual` from the entities (`on`, `level`, `color`, `unavailable`, `state`, `attrs`, `domain`, `night`, `at`: the item's world position). Components receive only `v`. Lit surfaces use `useLitMaterial`, halos `Glow`. `v.related` holds the extra entities (Scene passes one shared empty array to items without extras, so Visual is not recomputed needlessly), `v.interior` says whether a door or window sits in an interior wall.
- **Labels:** drei `Html` is not used (under React 19 each one is a separate root and throws errors). Labels live in a single DOM layer, `ui/PinLayer.tsx`; `LabelProjector` writes their `transform` every frame.

### Walls, rooms and openings

- **Wall thickness and corners:** walls are CENTERED on the room boundary. An exterior wall is 0.1 thick (half inside, half outside); a wall shared by two rooms is drawn by each room on its own side at half thickness (`WALL_IN` = 0.05), together a single wall. The inner face is always `WALL_IN` inside the boundary and aligned. Wall ends are extended by `WALL_IN` (`RoomMesh > Wall`, the room ghost too), so outer corners and the inner corner of an L have no gap, and straight runs simply overlap. (Walls inside the room made shared walls 0.2 thick and left a 10 × 10 cm hole in L corners.)
  - Everything measured from the inner face uses `WALL_IN`: `wallSnap` (item at inner face + depth/2 + 1 cm), `fitsRoom`, `resize.ts`, the auto plan (`generate.ts > onWall`), the ceiling strip. Doors and windows are measured from the room BOUNDARY (`APERTURE_INSET` 0.21; `wallSnap(..., aperture = true)`): their frames are centered on the boundary and cover the wall on both sides; the window sill is on the inner face.

- **Walls:** thickness 0.1, height 2.6. **Interior (dividing) walls are FULL height by default and are not cut while the camera rotates** (you should not see behind a dividing wall); the brick wall button in the map controls switches to low mode (0.38 m, sketch-like) (`useView.innerWalls`, `localStorage['homescape-inner-walls']`). Exterior walls facing the camera drop to 0.16 m, far ones stay full height; this is recomputed smoothly as the camera turns. In plan view every wall is low. Doors and windows (`useWallHeight`) follow the same rule: an interior door is full height with full walls and cut in low mode.
- **L, T, U shaped rooms:** a `Room` is a main rectangle (x, z, w, d) + optional `parts: Rect[]`. Everything that uses room geometry goes through the `geometry.ts` helpers: `rectsOf`, `inRoom`, `roomAt`, `bounds`, `roomArea` (area of the union), `labelPoint` (center of the largest part), `shiftRoom`. Never compute "inside the room" with `room.x + room.w`; you would miss the parts.
  - **Walls `wallRuns(room, rooms)`:** every part edge is split at all rectangle corners; for each segment the code looks 5 cm outside: the same room means no wall (union of parts), another room an interior wall, nothing an exterior wall. Consecutive segments of the same type merge. RoomMesh draws one `Wall` per run (vertical walls are not shortened at corners; the overlap is the same material and invisible). Openings come from `runOpenings(run, items)`. `wallSnap` only snaps to real walls.
  - **Rules:** an item's footprint must be inside the union and clear of the walls (`rules.ts > fitsRoom`: points every 10 cm, WALL_T in four directions); an item crossing the seam between parts is fine. Room overlap checks every part (`overlapsRoom(Rect | Rect[])`), the magnet snaps to every part of the neighbors. Doors (`doors.ts`) go on the longest shared part edge of two rooms.

### Lights and rendering

- **Room lights (`scene/roomLights.ts`):** three.js `pointLight` is NOT used (an unshadowed point light lights the far side of walls, and many of them are expensive). Instead `MeshStandardMaterial.prototype.onBeforeCompile` extends every standard material: up to 24 lights (`HS_MAX`, raised from 16 for windows in the walk) in shared uniform arrays (position + range, color + type, 4 room rectangles per light). Each light only lights surfaces inside **its own room's rectangles** (in L, T, U rooms the mask is not pulled in at the seams between parts but overlaps them by 5 mm, otherwise a dark line runs down the middle; other edges are pulled in by 1 cm: the outer faces of walls lie exactly on the boundary, so they fall outside the mask; walls are drawn inside the room through `wallRuns`). Light is clipped vertically too (`RoomLight.y`, `hsY`): indoor light (lamps, light through doors, daylight, alarm) stays between the active floor's floor and ceiling (-0.05 to 2.65 m); outdoor light is unbounded upward (clipping only horizontally let indoor light reach the roof above, the upper floor in the walk and the lower floor in View).
  - **Through open interior doors:** each (light, open interior door) pair gets a second entry: the same source, the neighbor room's rectangles and the door opening (`hsPortal`: plane, extent ±0.46 m, type); in the shader the ray must cross the door plane inside the opening and below 2.2 m (6 cm soft edges), so a door-shaped widening beam falls into the next room; no ambient term. Whether a door is open: `doorOpen` (the same rule as Door: sensor or cover when present, else open unless locked). The ceiling strip passes through doors as a point light.
  - **Falloff and corners:** point and line lights fall off in two terms: a bright pool about 1 m around the source `1.1 / (1 + 3d²)` and a soft spread across the room `0.62 / (1 + 0.12d²)`, plus a small even ambient of 0.11 (a single soft term lit the room evenly and dimmed lights did not seem to come from their source). In multi-part (L, T, U) rooms there is a line of sight test: the segment from the source to the surface is intersected with the part boxes (slab test) to find how far it stays continuously inside from the source; the length hidden behind a corner (0-0.6 m, soft) drops the light to the ambient level (20%). No extra cost in single-part rooms or for door spill.
  - **Limit and priority:** first every room's own lights (strongest first), then daylight in the walk, then door spill in the slots left (spill used to compete with main lights in one list sorted by power, so bright neighbors pushed a desk lamp out: the bulb glowed but the desk got no light). Spill from the same room through the same door merges into one entry (key `${door}>${room}`: power-weighted average position, summed color, longest range, a point light if the types differ).
  - **Types:** 0 point (soft falloff, wrapped Lambert and a little ambient on every surface in range; a pendant's range is the room diagonal + 1 m, filling the room), 1 downlight (downward cone), 2 ceiling strip (room-wide; wall tops bright, upward faces even), 3 line (strip LED: the source is the strip's closest point to the surface; `hsAxis` holds direction + half length along the item's local x axis), 4 daylight. Line lights: LED strip (2 m), counter LED (counter length), headboard (1.56 m), the mirror cabinet's lower strip. Through a door they become point lights.
  - **Type 4, daylight (walk only, `computeRoomLights(..., sky)`):** every window facing outside (no room or an outdoor room) and every open exterior door or garage door (sensor or cover open; an exterior door without a sensor is drawn closed and gives no light) gives sky light to its indoor room: the source is the point of the opening's rectangle nearest to the surface (axis `hsAxis`, room-facing normal and minus half height `hsPortal`), spreading along the normal (bright by the window, fading deeper, a little even ambient). Power: `WINDOW_POWER` × sky level × opening area × shade transmission (`shadePass`: curtain, roller, blind slat angle, zebra; from the bound cover's `current_position`); when the sun is on the outer side of that wall, the bounce of the patch it throws inside is added (warm color). In the walk by day, lamps are scaled by `FPS_DAY_FACTOR` (0.65).
  - The list comes from `computeRoomLights(level, entities, night)`: each lamp kind's local light point, power and range are in the `SPEC` table; the counter LED and TV backlight are faint point lights too. By day the contribution is 30%, at night full. `RoomLightSync` writes it on plan, HA and theme changes. It is disabled while thumbnails render (`withoutRoomLights`). Tests and diagnostics: `window.__homescape.roomLights()`.
  - **Strip LED look:** NEVER put spaced `Glow` halos along a strip. `effects.tsx > StripGlow` is the strip itself: a continuous band along local x with soft ends and edges (two crossed planes, visible from any angle; `textures.ts > lineGlowTexture`). `Wash` is the light on the surface the strip hits: the plane's top edge is bright and fades exponentially (`washTexture`); the group is rotated onto the wall (down or up), the worktop or the floor, 4-5 mm in front of the surface. Uses: LED strip (down and up the wall), under-cabinet (the worktop from back to front + the tile wall), plinth (floor), headboard (down the headboard; the behind kind up the wall), ceiling strip (1.3 m down each wall), mirror cabinet (the wall below).
  - No halos in front of lamps (`LightEmitter` was removed: it showed as dots in front of lights): the lamp body glows and the room light lights the room. The blue halo in front of the TV is gone too. The remaining `Glow` halos are small status lights. Floor lamps and wall lights are strong (power 4.6 / 5, range 8 m).
  - **Light textures are never drawn with canvas gradients** (`textures.ts > alphaTexture`, DataTexture): Chrome dithers gradients, which shows as speckles when magnified. Halos, the TV backlight, strip bands and surface washes compute every pixel from a smooth function.
  - Keep `Glow` halos small: a large halo sprite bleeds through to the other side of a wall. When you add a lit item, add its room lighting to `SPEC`; never put a `pointLight` in a component.
- **Lights and render:** `shadows="percentage"`, `NeutralToneMapping`. One set of ambient lights (`Scene.tsx > Lights`): hemisphere + directional sun/moon, whose colors and intensities (and the sky and fog colors) move between day (1.25 / 2.2) and night (bluish 0.55 / moon 0.6) in 0.6 s (`perf.skyBlend`: 0 day, 1 night). (Separate day and night light sets did not unmount cleanly when switching back to day and left the scene gray and dim.) At night the lamps are the main light source.
  - **Fog (`Scene.tsx > FogRange`):** the color is set in `Lights` (the same as the background), the range every frame in `FogRange`. In the orbit view it scales with the camera's distance to its target (`controls.distance`): 45-130 m up to `FOG.ref` (32 m), growing proportionally above it (the American sample home at 87 m: 122-352 m; a small home on a phone at 72 m: 102-294 m), the far end capped at 92% of the far plane (a fixed range faded large lots). **No fog in plan view**: the range is pushed past the far plane (never remove `scene.fog`: that recompiles every material). **In the walk** a fixed 45-130 m. The ground plane (`EditLayer > Ground`) is 1200 m so its edge never shows beyond the fog at low angles; the camera's far plane (400 m) clips it. Diagnostics: `window.__homescape.lighting().fog` ([start, end] m); `check:demo` tests the overview and the plan view.

### Interaction and controls

- **Controls:** game / city builder style.
  - **Mouse:** **left drag ROTATES**, **right or middle drag PANS** (like a map, on the ground plane), **Space + left drag also pans** (even over an item), the wheel zooms toward the pointer. Touch: one finger rotates, two fingers zoom and pan.
  - The **Rotate / Hand** buttons at the top of the map controls choose what left drag does (`useView.leftDrag`, `localStorage['homescape-left-drag-v2']`; the key is v2 so old pan preferences do not override the default). In Hand mode right/middle drag rotates, as does **⌥ or ⇧ + left drag**. Right and middle buttons always do the opposite of the left button's choice (`mapButtons(left, base)`). **Two-finger horizontal scrolling on a trackpad** rotates in every mode (horizontal wheel, `ButtonMap`).
  - Settled decision: left drag rotates by default, panning is right drag and Space. Do not change it (with left drag panning, people thought rotation was gone, and right drag is awkward on a Mac trackpad).
  - Mapping rule (`Scene.tsx > ButtonMap`): Space held: pan; ⌥/⇧ held (outside placement): rotate; placement or room drawing: the left button belongs to the scene; otherwise `leftDrag` (default `rotate`). While a camera key is held (`cameraKey()`), items and rooms are neither dragged nor selected.
  - camera-controls 3.1: panning on the ground plane is `ACTION.SCREEN_PAN` (horizontal = sideways, vertical = forward). `ACTION.TRUCK` lifts the target into the air on vertical drags; do not use it. `verticalDragToForward` was removed in 3.x (it only prints a warning).
  - `cameraApi.mapButtons` is called from the `ButtonMap` component INSIDE the Canvas and AFTER `CameraRig`. A `useEffect` outside the Canvas runs before the R3F children mount: the ref is empty and the mapping is silently skipped (this happened; a test caught it).
  - During placement or room drawing the left button belongs to the scene (the camera ignores it); the camera works with the right button, the wheel and the keyboard.
  - Click vs drag: selection happens only in `onClick` and only when `e.delta <= DRAG_PX` (4 px). Panning or rotating the camera and releasing never selects or deselects anything.
  - A room moves by dragging its floor only if it is **already selected** and in Edit mode. Dragging an unselected floor pans the camera.
  - Items drag directly in Edit; moving and history start once the pointer moves 4 px. The camera is off while dragging.
  - While Space is held, items, rooms, handles and tools receive no events; the camera pans even over an item.
  - Double click: focus a room or item; double click on empty ground: the whole home.
  - Keyboard (`App.tsx > useShortcuts`): **WASD** and the arrows pan (⇧ faster; in Edit the arrows nudge the selected item 5 cm, ⇧ 25 cm, the selected room 25 cm), **Q / E** rotate 45°, `+`/`-` zoom, `F` focus, `Esc` releases placement first, then the tool, then the selection, `R`/`⇧R` rotate the ghost while placing, else the selected item, `Delete` deletes, `⌘Z`/`⇧⌘Z`. Also `P` (right panel), `T` (roof), ⌘K / Ctrl+K or `/` (search).
  - The full list of controls is in the UI: the `?` card in the map controls (it also has rotate left/right buttons). A hint toast shows once on first open.
  - After a behavior change run `npm run check:controls` (intermediate screenshots go to `shots/`). In tests the drag start point must not land on furniture (the item would be dragged); the center of a room label is safe.
- **Selection look (`scene/Selection.tsx`):** no ellipse on the floor. A single selection gets (1) an inverted hull outline on every solid mesh of the item (a shell inflated along smoothed normals with its back faces drawn; a fixed 3.5 px on screen; pushed behind the body so only the outline shows; counted in `perf.outlines`), (2) the real 3D bounding box with thick lines drawn over everything, (3) the rules' footprint rectangles (`rules.ts > localFootprints`, two parts for an L counter) with a translucent fill and line. Area selection: a dashed box and no outline; hover: only a faint footprint; an invalid move: everything in alarm red. Measuring happens on the next frame (meshes built, matrices updated). Do not use drei `Outlines`: inside a portal it could not read the screen size and drew a giant blob over the scene.
- **Placement (build bar, `ui/BuildBar.tsx`):**
  - Press and hold a card, drag it into the scene, release: placed. Tap a card and release to enter click-to-place mode; the item goes where you click in the scene. Releasing with ⇧ held keeps the tool active (except items bound to an HA entity, which are placed once). Right click or Esc cancels. Releasing outside the canvas cancels.
  - Input `ui/usePlacementInput.ts` (window-level capture listeners), ghost `scene/Ghost.tsx` (every frame: a ray onto the y=0 plane, a 5 cm grid, wall items snap to a wall within 1 m, desktop items climb onto a surface), result `usePlacement.result`. Tag `PinLayer > GhostTag`: green "Name · drop", red "Name · reason". While placing, room labels fade, the selection label hides and the selection clears.
  - Rules `model/rules.ts > checkItem`, each failure with a short reason: the item must be inside a room; a wall item must be on a wall; the footprint must not stick out of the room; it must not collide with another item in the same layer (the reason names it); it must not enter a door's clearance (nor a door's swing area be taken). Door zone `doorZone`: opening width 0.92 m, 0.9 m into the room (the leaf), 0.35 m into the room behind; rugs, ceiling and desktop items are exempt. Layers: floor, wall, ceiling (pendant), rug, on a surface; different layers never collide (a sofa on a rug, a monitor on a desk, a pendant on the ceiling). Chairs fit under desks (`TUCKS`).
  - Dragging an existing item uses the same rules: the outline turns red; dropping in an invalid place returns it through `revertCheckpoint()` with a toast.
  - Room cards: preset sizes (`ROOM_PRESETS`); the ghost snaps to neighboring edges within 35 cm through `magnetRoom` and turns red on overlap. The "Free draw" card opens the drawing tool.
  - **Room overlap is blocked on every path:** ghost, free drawing (the draft turns red; anything under 1 × 1 m is rejected too), moving a room (it does not move into an overlapping position, toast), resizing with handles, and numeric width/depth in the Inspector. Check `overlapsRoom` (EPS 1 cm; sharing an edge is fine).
  - Thumbnails: `scene/Thumbs.tsx` renders each kind's real component on an offscreen 160 px canvas (lights and screens on), frames it by the bounding box of the visible meshes only, stores it with `toDataURL` and removes itself when done. Until then the card shows a Lucide icon.
  - In Edit the framing accounts for the build bar (`camera.ts > viewport().used`) and reframes on mode change. On phones the Edit help card is hidden (it covered the scene).
- **Camera:** `cameraApi.frame(rooms)` frames using the aspect ratio, the right panel and, in Edit, the build bar. `setFocalOffset` sign rule: +x moves the scene left, +y moves it up (verified with screenshots). `camera.ts` is in the main bundle: never import three or drei as values there (for a vector use `controls.camera.position.clone()`); `ACTION` comes from the scene as a parameter.
- **Quick pill and clickability:** a single pill: state in `ui/quickState.ts` (no three: `useQuick`, `useQuickId`, `quickTarget`, `hasQuick`, `pointAt`, `placePill`), content `ui/QuickPill.tsx` + `ui/QuickActions.tsx` (mounted once in App inside `#quick-layer`, OUTSIDE the scene's event container, so presses never reach the camera controller), position from `scene/QuickAnchor.tsx` (inside the Canvas; writes on every rendered frame without React re-renders and touches the DOM only when the position changes). (Earlier every item had its own drei `Html`: a new React root on every hover, the pill at a fixed height above the item center, sometimes under the panels.)
  - **One thing at a time:** hover shows only the quick pill; a click (selection) shows only the detail card on the right: that item's pill closes (`useQuickId`: the hovered item, none if it is selected) and in View the status label above the item does not show either (`ui/PinLayer.tsx > SelectedTag`, for items with a pill; `data-selected-tag`); hovering another item while one is selected shows that item's pill. When the pointer reaches a pet, the pill of the item underneath closes at once (`dismiss`; the pill must not cover the pet).
  - **Pill:** left, the main button by kind (`QuickMain`, `data-quick-toggle`: power; lock, cover, run for scenes / scripts / buttons, start / dock for vacuums, arm / disarm for alarms); middle, name and state (a yellow dot when on) with readings (`quickReadings`: temperature, humidity, power, battery); right, extras by kind (`QuickExtras`: a brightness slider `data-quick-slider` for a light that is on, fan speed, climate −/+ `data-quick-minus` / `data-quick-plus` with step and limits from the entity, media play / pause, cover open / close with stop while moving, vacuum pause; sliders send every 0.25 s while dragging and the last value on release), a door button for cabinets (counter, wardrobe, dresser: `OPENS`; `data-quick-doors`, Lucide `DoorClosed` / `DoorOpen`, `useBins`) and a details arrow (`data-quick-details`: selects, opens the card, closes the pill; labeled "Details" on a pill opened by touch). The first pill waits 90 ms, so moving across items does not flash pills.
  - **Position:** from the on-screen box of the item's body (visible raycastable meshes, no glows or light pools; `ItemNode` registers its inner group in `scene/hoverTargets.ts > quickObjects`) and the pointed spot (`pointAt`, stored in the item's group so it sticks to the same part of the item as the camera turns): horizontally aligned with that spot, above the item's top but at most 40 px above the pointer (not up at a pendant's cord), else below the pointer; never over the screen edge, the right panel on wide screens (`panelSpace`), the open bottom card on narrow ones, the bars or the info tiles (`#kpi-tiles`); hidden when the item leaves the screen. It closes 0.42 s after the pointer leaves the item; with a pill open, switching items takes 0.14 s (0.32 s from the item to the pill).

Never trust a click event's own type: iPad WebKit can report a finger's click as "mouse", which sent taps down the select path so the quick pill never appeared on a live home (the sample home toggles on any click, which hid the bug). Taps tolerate sliding (`clickSlop`: 14 px for touch and pen, 4 px for mouse; items, ground, pets). A tap toggles an item directly, except a cabinet with a bound light (a counter with under-cabinet LED), which opens the pill with both the LED and the doors; a cabinet without a light opens its doors; with a mouse a click opens the doors and the LED is in the hover pill. In Edit everything is selectable (the selection label has the edit buttons). ### Performance

- Measure with `npm run perf`. Where it stands: 0 fps while idle once the scene settles (it used to render 60 fps with ~680 draw calls and a shadow map pass per frame), about 34k triangles (from 162k), shadows only when the scene changes.
- **`frameloop="demand"`:** the scene renders only when something changes (`scene/frame.ts`). drei CameraControls requests frames for camera motion, R3F for object props changed through React. **Anything animating inside useFrame must call `state.invalidate()` until it finishes**, and if its target changes from React, add `useEffect(() => invalidate(), [target])` (examples: `useEased`, wall height, `useWallHeight`, the selection ring, the robot vacuum turning). Otherwise the animation freezes. To request a frame from the UI call `kick()` (label registration does this).
- **Ambient animations** (mist, airflow, motion ripples, propellers, camera LEDs, flicker, vacuum) register with `useAmbient(active)` (`kit/effects.tsx`); `AmbientTicker` requests 24 fps. Never add an animation that requests 60 fps continuously (a pulsing selection ring was removed for this reason).
- **Shadows:** `ShadowManager` sets `shadowMap.autoUpdate = false`; shadows redraw when the plan, theme, floor, HA state or plan view change and during shape-changing transitions (`markShadows`), not while the camera rotates (the sun is fixed).
- **Resolution:** at most 1.5x (instead of 2x on Retina), temporarily lower while the camera moves (`regress` + `AdaptiveDpr`, `performance.min 0.6`).
- **Geometry cache** (`kit/primitives.tsx`): boxes, rounded boxes, cylinders and spheres of the same size share one geometry; rounded boxes use `RoundedBoxGeometry` with 2 segments instead of drei `RoundedBox`. Cached geometry is never disposed.
- **HA updates:** `ItemNode` is wrapped in `memo`; when a sensor changes only that item rebuilds (unchanged entity objects keep their reference, in both the demo and the live source). `LabelProjector` writes no styles to unchanged labels.
- **Lite mode** (feather icon in the top bar, `useView.lite`, `localStorage['homescape-lite']`): no shadows, no ambient animation (it only advances while the camera moves), resolution 1x, at most 3 point lights, flat panels instead of frosted glass (`body[data-lite]`). The shadow setting changes, so the canvas remounts through `key`.
- Headless Chrome uses software WebGL, so `npm run perf` does not show GPU gains (resolution, shadows) in full; frame counts, main thread time, draw calls and triangles are what to compare.
- More rules: no setState inside `useFrame`; one shared material per color (`mat`); materials that change with state are disposed when the component unmounts.

### Homes, floors, Dashboard, walk and weather

- **Multiple homes:** `layoutStore` keeps `homes: HomeEntry[]` + `homeId` (persistent; empty in old saves, which means a single default home: `homesOf` / `activeHomeId`). The active home's plan stays in `layout` (the whole app reads it); the other homes' plans and last floors live in `homes`; `addHome` (empty plan, Edit mode), `switchHome` (undo history resets), `renameHome`, `deleteHome` (the last home cannot be deleted). No migration: the new fields are optional. All homes share the same HA connection. UI: `ui/HomeMenus.tsx > HomeSwitcher` in the top bar.
  - **Switching homes is a camera flight**, never an overlay: `ui/homeSwitch.ts > switchHomeAnimated(fn, dir, peek)` hands the request to `scene/HomeFlight.tsx` (`registerHomeFlight`; without a scene, in the walk or with reduced motion it switches at once). Homes behave as if side by side in one world, but only the active one is drawn and the target is never seen before the switch. (1) Takeoff, 1.1 s: the camera rises (1.5 × the framing distance of both homes, at most 200 m; `peek` gives the destination's plan), tilts to 0.35 rad, turns to the default heading, resets the focal offset and glides sideways (next home to the right, previous to the left: `homeDir`) until the old home's box (floors, roof, shadow margin) has left the real camera's view (`clearance`, half-meter steps), plus 2 m. (2) Switch: `fn` runs while the old home is out of frame, and the camera moves into the new home's coordinates with that home just outside the frame ahead (the ground is uniform, so nothing jumps; motion continues with a clamped frame time if the rebuild takes a frame). (3) Landing, 1.5 s: it slows and descends into `cameraApi.framePose`. During the flight camera input is off, `maxDistance` is wide and `CameraRig` requests wait (`camera.ts > homeFlight.active`). A new pick during takeoff only changes the target; during landing it starts a new flight from the current pose. Rebuilding the sample home while in it does not fly. ### Sound

- **Recordings:** natural and mechanical sounds are **AI-generated recordings made locally** with Stable Audio 3 Small-SFX (effects) and Small-Music (speaker music, TV menu), Stability AI's open-weights model, on MLX (Apple Silicon). The model lives outside the repository (default `SA3=../stable-audio-3/optimized/mlx`; weights `stabilityai/stable-audio-3-optimized`, no login; Stability AI Community License). `tools/sfx/build.py` (run with SA3's `.venv` Python; `CATALOG` holds each sound's English prompt, duration and take count; raw WAVs stay in `$SA3/output/homescape/`): loops lose 1 s at both ends plus any silent or fading tail (or a hand-set `region`) and close with an equal-power crossfade, keeping the take with the steadiest level; short sounds keep the loudest event cluster from takes with a clear event (`clarity`: envelope peak at least 18 dB over the median; short durations can come out as hiss, so they are requested at 3-5 s and `keep` of 5-6 takes survive); footsteps are sliced from a 12 s walk. Check with spectrograms (`tools/sfx/spectro.py`; an agent cannot listen). Output: mono, level-matched AAC `.m4a` (96 kb/s, gapless in Chrome and Safari) in `public/sounds/`, listed in `src/audio/samples.json`. One sound: `$SA3/.venv/bin/python tools/sfx/build.py <id>` (change its prompt or take count for a new seed); `--process` only reprocesses.
- **Sample layer** `audio/samples.ts` (`voiceSample`, `shotSample`, `SCATTER`: page turns, rustling, toys, squirrels played now and then; downloaded on first need, short ones preloaded when sound is enabled): loops play from a random offset with a slightly different pitch per source (except music and TV), short sounds pick one of their variants (never the same twice in a row) with a slight pitch change. Sounds without a recording are synthesized (`src/audio/voices.ts`, `shots.ts`); electronic beeps (AC remote, microwave and appliance done melodies, alarm armed, robot vacuum, TV power on, smoke detector, water leak) are synthesized on purpose.
- **Engine** (`audio/engine.ts`): one AudioContext (created on the first touch, a browser rule; asleep while the tab is hidden, suspended while sound is off), eight categories, each with its own bus, switch and level (`Bus`: appliances and climate, TV and music, doors, keys and cabinets, alerts and notifications, people, animals (passing ones too), outdoor and weather, interface; picked from the sound's name via `voiceBus` / `shotBus`, or passed by the caller when context matters: a stove's sizzle is an appliance, a person stirring is people; bus gain = base share × level²; an older four-bus setting migrates), master gain `volume² × MAKEUP` and a compressor. Sounds are positioned in 3D (`PannerNode`, inverse distance, `ROLLOFF` 1.15): the listener is at the eye in the walk, else a third of the way from the camera's target toward the camera (at least 2.5 m; `camera.ts > cameraApi.pose`), so zooming in brings that room forward. In the walk other rooms are muffled (`setMuffler`: low-pass and loss; through an open or sensorless door 0.3, closed or unconnected 0.6, inside vs outside 0.72, an open window or front door 0.45). At most `MAX_LOOPS` (14) loops play, the loudest heard (`setLoops`); short sounds beyond 45 m are skipped. Settings (on, level, buses) in `localStorage` `homescape-sound`.
- **Loops** (`voices.ts`) cover running appliances, water, climate devices, electronics, media (the TV program `music.ts > talk`: two muffled voices over music; the TV menu; speakers playing their own music, `music.ts > music`, a different song each), machines, alarms, people's activities, animals and outdoor ambience (birds by day, crickets at night, wind, rain from `weather.*`, city hum near roads). Night ambience (`SoundScape.tsx > ambience`, the scene's night rule): a quiet bed (`night`), frogs near a pond (`frogs`), an owl every 28-75 s (`owl`), a far dog every 45-120 s (`barkFar`); street life adds `carDrive` and `kids`.
- **Short sounds** (`shots.ts`): switches and plugs, doors, windows, locks, doorbell, cabinet doors and drawers (opened in View or the walk by `ItemNode`; not for the mass opening on a mode switch), appliance events (coffee grinder, TV on and off, AC beep, done melodies, kettle click, vacuum melodies), alarm armed and disarmed, footsteps per surface (parquet, hard floor, carpet, grass, gravel, water, stairs), pet sounds, a passing car (only with street life off), thunder, owl, far dog, trampoline and interface sounds (placed, deleted, rotated).
- **Wiring** (`audio/SoundScape.tsx`, inside Scene, draws nothing): about 3 times per second it reads the plan, HA, people (`peopleDebug`; an activity's sound comes from in front of their hands), pets (`petsDebug`; a visiting dog barks now and then, the cat meows) and the weather. Running devices: `running` (here a power sensor above 8 W) and `busy` for machines on plugs (an on plug alone does not mean running: a power sensor or the machine's own state decides). HA state changes play a short sound (`onEntities`; never on first load, at most 3 light clicks at once). Footsteps: people on each half of the walk cycle (`People.tsx`, `audio/floor.ts > stepAt`), the walk at the bottom of the head bob (`FpsControls.tsx`); getting up from the toilet flushes; pet reactions come from `Pets.tsx > reactSound`.
- **UI:** a sound button in the top bar (`#sound-toggle`, `ui/SoundMenu.tsx`: the sound switch, master level, each category's switch `#sound-bus-<category>` and level slider `#sound-level-<category>`); on phones a sound on/off row in the "More" menu. Since an agent cannot listen, levels are measured offline (`engine.ts > measure`, `OfflineAudioContext`); developer lab **sounds** `src/dev/SoundLab.tsx` (`#sounds`) plays every sound one by one. Test hooks `sound()` (bus gains in `gains`; a browser does not process a bus without input, so a gain only updates while that category plays), `soundUnlock()`, `soundNight()` (owl and far dog right away), `soundMeasure()`, `soundPlay()`; test `npm run check:sound`.

## 6. Auto plan (generate.ts)

- Room type from the area name or icon: living, kitchen, bedroom, bathroom, entry, study, other (name keywords in several languages, since entity and area names come in the user's language).
- **Interior doors first, then furniture:** `connectRooms` starts at the entry (else the living room) and grows like a tree; every room gets one door from its best neighbor (halls and living rooms give passage, bathrooms and bedrooms do not: `rank`). The shared wall must be at least 1.3 m; the door is sought near a corner (front/right end first, 5 cm steps), and the child room is connected first. A template item that lands in front of a door slides along its own axis (`SHIFTS`), or is skipped if there is no room. (With furniture placed first, bedrooms could only be reached through bathrooms and studies not at all.)
- Door sensors bind to an unbound door in the same room (exterior door first, then interior).
- Climate items (AC, boiler) get the temperature and humidity sensors of the same HA area as **extras** (at most 3); the room value and the card show them.
- Each room type has a default size and floor; rooms are laid out in rows (about 14 m per row), depth equalized within a row, and the house is centered at the origin.
- Each room type has a furniture template (living: TV, sofa, coffee table, rug, armchair, bookcase, plant; kitchen: fridge, sink, counter, stove, dining table; ...). Unbound device items in a template (TV, monitor, desk lamp, mirror light, counter LED, door) bind to entities as they arrive.
- Entity to kind, `kindFor`: domain, `device_class`, name keywords and the model from the device registry (`registry.entityModel`; for a HomePod named after a room). Configuration switches (AdGuard, Zigbee, alarm HomeKit bridge, segments) are skipped.
- Entities without an area: first a room name inside the entity name, then a sensible room for the kind (a TV light in the TV's room, climate in the living room, the alarm at the entry). Otherwise they go to the unplaced list; in Edit the helper card's "Place" opens the ghost and drops the item where you click (bound to the entity).
- Singular kinds (TV, console, boiler, diffuser, door, temperature sensor, alarm) are not added twice to a room; a second entity goes to the unplaced list.
- Room temperature and humidity (`ui/useHome.ts`): entities in the room's HA area + every entity bound to items in the room (main and extra), `sensor.*` with the matching `device_class`. The "Doors / windows" KPI is open when any door or window sensor or cover bound to an item is open.
- Controls (`ha/actions.ts`): `button`/`input_button` call `press`, `scene`/`script` call `turn_on` ("Run"); readable domains such as sensor, number and select are shown as values only (`isReading`).
- Processing order by domain: climate, media_player, humidifier, light, ..., switch last (when a smart plug powers a device, the real device binds first).

## 8. Internationalization

Everything lives in `src/i18n/index.ts`.

- UI text is written in English and wrapped in `t()`; the English text itself is the key, so English needs no dictionary and unknown keys fall back to English. Translations are in `src/i18n/locales/<code>.json` (English text to translated text); a value is a string or, for counted phrases, an object of plural forms keyed by `Intl.PluralRules` categories (zero, one, two, few, many, other).
- 14 languages (`LANGUAGES`): en (default), de, es, fr, it, nl, pl, pt, ru, tr, hi, ja, ko, zh. To add one, add it to `LANGUAGES` and add a locale file with every key.
- The language is chosen once at startup (`initI18n`; `main.tsx` awaits it before importing the app, so module-level `t()` calls are translated too): the saved choice from the language menu (`localStorage` `homescape-lang`), else the HA user's language when Homescape runs inside HA (read from the same-origin parent frame), else the first supported device language (`navigator.languages`, base tag: pt-BR becomes pt), else English. Changing the language saves the choice and reloads the page (`setLang`; `null` returns to automatic).
- `npm run i18n:check` (`scripts/i18n-check.mjs`, also in CI) collects every literal passed to `t()`, `tn()` and `msg()` and reports missing keys, unused keys and placeholders that do not match the English text; it also lists `t()` calls with a non-literal argument for review (`--keys` prints every key with a source location as JSON, for translators).

Rules:

- One sentence per `t()` call. Never concatenate translated pieces or build a sentence from fragments; word order differs between languages.
- Variable parts are placeholders: `t('{name} turned off', { name })`. Numbers passed as placeholders are formatted for the language.
- Counted phrases use `tn(count, one, other, vars?)`: `tn(n, '{count} light', '{count} lights')`; the `other` form is the key, and translations give one form per plural category of their language.
- Texts kept in tables or constants are marked with `msg()` (returns the text unchanged, so the checker sees it) and translated with `t()` where they are shown: `const LABEL = { a: msg('Clear') }`, then `t(LABEL[k])`.
- Data from Home Assistant (entity, area and user names) and names from the user's plan are never translated. Demo data is the exception: its English names are translated at load time (`src/demo/snapshot.ts > SAMPLE_TEXTS`, keep it in sync with `sample-snapshot.json`; `american.ts`).
- Numbers for display go through `formatNumber(n, maxDigits?, minDigits?)` (null or NaN shows "-"); `currentLang()` is a valid locale for other `Intl` and `toLocaleString` calls. Case-insensitive search and matching use `lower()`. For upper case use CSS `uppercase` (`<html lang>` is set, so language rules apply) rather than `toUpperCase()`.
- Expect longer text than English: buttons, segmented controls and rows truncate instead of overflowing (see `DESIGN.md`).

## 9. Code rules

- TypeScript `strict`, `verbatimModuleSyntax` (types through `import type`), `erasableSyntaxOnly` (no enums).
- `@/` = `src/`. Components small and single-purpose.
- Style: no semicolons, single quotes, lines up to about 200 characters. There is no formatter config: never run a formatter, and do not reformat files you did not change.
- Everything is in English: identifiers, comments (short, saying why), test messages, docs and the source UI text. The only Turkish in the repository is the Turkish translation (`src/i18n/locales/tr.json`).
- No machine-specific absolute paths (contributors may be on Windows). The HA address goes in `.env.local`.
- Never write secrets (tokens) into files or code.
- AI agents access a real HA read-only: no service calls, no automation or setting changes. The person runs live control tests.
- Commit messages in English, imperative mood ("Add weather effects"), and never with AI attribution lines (no co-author or "generated with" trailers).
- Never add files whose names differ only by case (`streetLife.ts` next to `StreetLife.tsx`): case-insensitive file systems (macOS, Windows) resolve the wrong one.
- Known lint warnings: `kit/primitives.tsx` and `kit/effects.tsx` export helpers next to components, which triggers a "fast refresh" warning; harmless (the helpers could move to separate files). The `THREE.Clock` deprecation warning in the console comes from inside R3F.
- **zustand 5 selectors must not return a new object or array on every call** (`useLayout((s) => ({ a, b }))` loops forever and blanks the page). Select values separately or use `useShallow`. (This happened in ResetDialog; a test caught it.)
- Dialogs opened from inside a `z-30` layer such as the toolbar use `createPortal(..., document.body)`; otherwise the right card and the build bar stay above the backdrop.
- Do not mutate objects returned by hooks (for example `useThree().camera`, the controls) inside a component; oxlint's `immutability` rule warns. Take them from the `useFrame` argument or move the change into a module function such as `cameraApi`.
